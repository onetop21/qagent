# QAgent 헌법

## 핵심 원칙

### I. 테스트 우선 개발 (필수)

모든 기능 개발은 테스트를 먼저 작성하고 구현해야 합니다.

- 테스트 작성 → 사용자 승인 → 테스트 실패 확인 → 구현 순서를 엄격히 준수해야 합니다
- 매 태스크 작업 완료 후 반드시 빌드 및 유닛 테스트를 실행해야 합니다
- Red-Green-Refactor 사이클을 따라야 합니다
- 테스트 없는 코드는 프로덕션에 배포할 수 없습니다

**근거**: QA 자동화 도구의 신뢰성은 철저한 테스트에서 나옵니다. 테스트를 먼저 작성함으로써 요구사항을 명확히 하고, 회귀 버그를 방지하며, 리팩토링 시 안전성을 확보합니다.

### II. 간결성 우선

코드는 목적에 맞게 최대한 간결하게 작성해야 합니다.

- YAGNI(You Aren't Gonna Need It) 원칙을 따라야 합니다
- 불필요한 추상화나 과도한 설계를 지양해야 합니다
- 명확하고 읽기 쉬운 코드를 작성해야 합니다
- 복잡도 증가는 반드시 정당한 사유가 있어야 합니다

**근거**: QA 도구는 사용자의 워크플로우를 개선하는 것이 목표입니다. 복잡한 코드는 유지보수 비용을 증가시키고 버그 발생 가능성을 높입니다. 간결한 코드는 이해하기 쉽고, 테스트하기 쉬우며, 수정하기 쉽습니다.

### III. 통합 테스팅

새로운 기능, 계약 변경, 서비스 간 통신에는 통합 테스트가 필요합니다.

- 새로운 라이브러리나 모듈에는 계약 테스트를 작성해야 합니다
- API 변경 시 계약 테스트를 업데이트해야 합니다
- 외부 서비스 통신에는 통합 테스트를 포함해야 합니다
- 공유 스키마 변경은 통합 테스트로 검증해야 합니다

**근거**: QAgent는 Gemini CLI와 통합되어 작동하므로, 통합 지점에서의 신뢰성이 중요합니다. 통합 테스트는 시스템 간 상호작용이 예상대로 작동함을 보장합니다.

### IV. 관찰 가능성

모든 기능은 디버깅과 모니터링이 가능하도록 설계해야 합니다.

- 구조화된 로깅을 사용해야 합니다
- 에러는 명확한 컨텍스트와 함께 기록되어야 합니다
- 중요한 작업 흐름은 추적 가능해야 합니다
- 텍스트 입출력 프로토콜을 통해 디버깅 용이성을 확보해야 합니다

**근거**: QA 도구는 문제 진단과 해결이 신속해야 합니다. 충분한 로깅과 관찰 가능성은 문제 발생 시 빠른 원인 파악과 해결을 가능하게 합니다.

## 문서화 요구사항

### 한글 문서화

모든 문서, 주석, 커밋 메시지는 한글로 작성해야 합니다.

- README, 사양서, 계획서 등 모든 프로젝트 문서는 한글로 작성해야 합니다
- 코드 주석은 한글로 작성하되, 변수명과 함수명은 영어를 사용해야 합니다
- 커밋 메시지는 한글로 작성해야 합니다
- 에러 메시지와 로그는 한글 또는 영어를 사용할 수 있습니다

**근거**: 팀원 간의 원활한 의사소통과 문서 이해도 향상을 위해 모국어인 한글을 사용합니다.

### 명확한 사양 정의

모든 기능은 구현 전에 명확한 사양이 정의되어야 합니다.

- 사용자 시나리오가 우선순위와 함께 정의되어야 합니다
- 기능 요구사항이 검증 가능한 형태로 작성되어야 합니다
- 성공 기준이 측정 가능해야 합니다

**근거**: 명확한 사양은 불필요한 재작업을 방지하고, 구현 방향을 일관되게 유지하며, 테스트 케이스 작성의 기준이 됩니다.

## 개발 워크플로우

### 태스크 기반 개발

작업은 독립적이고 검증 가능한 태스크 단위로 분할되어야 합니다.

- 각 태스크는 완료 후 반드시 빌드 및 유닛 테스트를 실행해야 합니다
- 태스크 완료 시 즉시 커밋해야 합니다
- 병렬 처리 가능한 태스크는 [P] 태그로 표시해야 합니다
- 각 태스크는 독립적으로 테스트 가능해야 합니다

**근거**: 작은 단위로 작업을 나누고 즉시 검증함으로써 문제를 조기에 발견하고, 변경 이력을 명확히 하며, 협업 효율을 높입니다.

### 지속적 품질 유지

배포 환경은 항상 안정적으로 유지되어야 합니다.

- 메인 브랜치는 항상 배포 가능한 상태여야 합니다
- 모든 PR은 빌드 및 테스트 통과 후 병합되어야 합니다
- 배포 전 통합 테스트를 실행해야 합니다
- 배포 후 모니터링을 수행해야 합니다

**근거**: QAgent는 다른 개발자들의 워크플로우에 영향을 주는 도구이므로, 안정성이 최우선입니다. 지속적으로 배포 가능한 상태를 유지함으로써 신속한 배포와 롤백이 가능합니다.

### 버전 관리

MAJOR.MINOR.PATCH 형식의 시맨틱 버저닝을 따라야 합니다.

- MAJOR: 호환성을 깨는 API 변경
- MINOR: 하위 호환되는 기능 추가
- PATCH: 하위 호환되는 버그 수정

**근거**: 명확한 버전 관리는 사용자에게 변경 사항의 영향도를 알려주고, 의존성 관리를 용이하게 합니다.

## 거버넌스

### 헌법 우선순위

이 헌법은 모든 개발 관행과 의사결정에 우선합니다.

- 모든 PR과 코드 리뷰는 헌법 준수 여부를 검증해야 합니다
- 헌법 위반 시 명확한 정당화가 필요합니다
- 복잡도 증가는 Complexity Tracking 표를 통해 문서화되어야 합니다

### 개정 절차

헌법 개정은 다음 절차를 따라야 합니다.

1. 개정 제안 및 근거 문서화
2. 팀 검토 및 승인
3. 버전 번호 업데이트 (시맨틱 버저닝)
4. 영향받는 템플릿 및 문서 동기화
5. 마이그레이션 계획 수립 (필요시)

### 버전 정책

헌법 버전은 시맨틱 버저닝을 따릅니다.

- MAJOR: 하위 호환되지 않는 원칙 제거 또는 재정의
- MINOR: 새로운 원칙/섹션 추가 또는 실질적 확장
- PATCH: 문구 명확화, 오타 수정, 의미 변경 없는 개선

### 준수 검토

정기적인 헌법 준수 검토를 수행해야 합니다.

- 분기별로 헌법 준수 상태를 검토합니다
- 위반 사례를 수집하고 개선 방안을 논의합니다
- 필요시 헌법을 개정하거나 교육을 실시합니다
