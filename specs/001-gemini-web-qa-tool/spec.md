# Feature Specification: Gemini 웹 QA 자동화 도구

**Feature Branch**: `001-gemini-web-qa-tool`
**Created**: 2025-10-21
**Status**: Draft
**Input**: User description: "Gemini와 Playwright MCP를 이용한 웹서비스 QA 테스팅 도구"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - PRD 기반 자동 테스트 실행 (Priority: P1)

QA 엔지니어는 PRD 문서를 도구에 등록하면, 자동으로 테스트 케이스가 생성되고, 웹 서비스에 대한 QA 테스트가 실행되어 결과 리포트를 받습니다.

**Why this priority**: 도구의 핵심 가치 제안입니다. PRD에서 테스트 케이스 생성, 테스트 실행, 리포트 작성까지의 전체 플로우가 작동해야 MVP로서 가치를 제공할 수 있습니다.

**Independent Test**: PRD 문서를 업로드하고, 대상 웹 서비스 URL과 로그인 정보를 입력한 후, "테스트 실행" 버튼을 클릭하면 테스트가 완료되고 리포트가 생성되는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** QA 엔지니어가 PRD 파일(Markdown 또는 PDF)을 준비했을 때, **When** 도구에 PRD를 업로드하면, **Then** PRD 내용이 파싱되고 테스트 케이스 목록이 자동 생성됩니다
2. **Given** 테스트 케이스가 생성되었을 때, **When** 웹 서비스 URL과 로그인 정보(아이디/비밀번호)를 입력하고 "테스트 실행"을 클릭하면, **Then** 브라우저가 자동으로 웹 서비스에 접속하고 로그인합니다
3. **Given** 웹 서비스에 로그인한 상태일 때, **When** 각 테스트 케이스가 순차적으로 실행되면, **Then** 각 테스트의 성공/실패 결과가 기록됩니다
4. **Given** 모든 테스트가 완료되었을 때, **When** 테스트 실행이 종료되면, **Then** QA 리포트(성공률, 실패한 케이스 목록, 스크린샷 포함)가 생성됩니다

---

### User Story 2 - AI 기반 테스트 케이스 증강 및 관리 (Priority: P2)

QA 엔지니어는 기본 테스트 케이스에 AI가 생성한 추가 테스트 케이스와 엣지 케이스를 확인하고, 필요에 따라 수정, 추가, 삭제할 수 있습니다.

**Why this priority**: 테스트 커버리지를 높이고 예상치 못한 버그를 발견하는 데 중요하지만, P1의 기본 테스트 실행 기능이 먼저 작동해야 합니다.

**Independent Test**: PRD로부터 생성된 기본 테스트 케이스 목록을 확인하고, "AI 증강" 버튼을 클릭하여 추가 테스트 케이스와 엣지 케이스가 생성되는지, 그리고 이를 편집/삭제할 수 있는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** 기본 테스트 케이스가 생성되었을 때, **When** "AI 테스트 케이스 증강" 버튼을 클릭하면, **Then** Gemini API를 통해 추가 테스트 케이스가 생성됩니다
2. **Given** 테스트 케이스 목록이 표시될 때, **When** "엣지 케이스 생성" 버튼을 클릭하면, **Then** 경계 조건 및 예외 상황에 대한 엣지 케이스가 추가됩니다
3. **Given** 테스트 케이스 목록이 표시될 때, **When** 사용자가 특정 테스트 케이스를 선택하고 "편집"을 클릭하면, **Then** 테스트 단계 및 예상 결과를 수정할 수 있습니다
4. **Given** 테스트 케이스 목록이 표시될 때, **When** 사용자가 "새 테스트 케이스 추가" 버튼을 클릭하면, **Then** 빈 테스트 케이스 폼이 나타나고 내용을 입력할 수 있습니다
5. **Given** 테스트 케이스 목록이 표시될 때, **When** 불필요한 테스트 케이스를 선택하고 "삭제"를 클릭하면, **Then** 해당 테스트 케이스가 목록에서 제거됩니다

### User Story 3 - 실시간 테스트 진행 상황 모니터링 (Priority: P3)

QA 엔지니어는 테스트 실행 중 웹 브라우저 화면을 통해 현재 어떤 테스트가 진행 중인지, 각 단계별 실행 상태를 실시간으로 확인할 수 있습니다.

**Why this priority**: 사용자 경험을 향상시키고 디버깅을 용이하게 하지만, 테스트 실행 자체가 먼저 작동해야 합니다.

**Independent Test**: 테스트를 실행한 후, 진행 상황 화면에서 현재 실행 중인 테스트 케이스 번호, 진행률, 각 단계의 성공/실패 상태가 실시간으로 표시되는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** 테스트가 실행 중일 때, **When** 진행 상황 화면을 확인하면, **Then** 전체 테스트 개수 대비 현재 진행률(예: 5/20 테스트 완료, 25%)이 표시됩니다
2. **Given** 테스트가 실행 중일 때, **When** 각 테스트 케이스가 실행되면, **Then** 해당 테스트의 각 단계별 실행 상태(대기 중, 진행 중, 완료, 실패)가 표시됩니다
3. **Given** 테스트가 실행 중일 때, **When** 브라우저 화면을 확인하면, **Then** Playwright를 통해 제어되는 실제 웹 브라우저 화면이 표시되고 현재 수행 중인 동작이 시각적으로 보입니다
4. **Given** 테스트 실행 중 오류가 발생했을 때, **When** 진행 상황 화면을 확인하면, **Then** 실패한 테스트 케이스가 강조 표시되고 오류 메시지가 표시됩니다

---

### User Story 4 - 외부 테스트 케이스 파일 가져오기 및 포맷 변환 (Priority: P4)

QA 엔지니어는 기존에 작성한 테스트 케이스 파일(Excel, CSV, JSON 등)을 도구에 업로드하면, 자동으로 도구의 표준 포맷으로 변환되어 테스트를 실행할 수 있습니다.

**Why this priority**: 기존 테스트 자산을 재활용할 수 있어 유용하지만, 새로운 PRD 기반 워크플로우가 먼저 안정화되어야 합니다.

**Independent Test**: 기존 Excel 또는 CSV 형식의 테스트 케이스 파일을 업로드하고, 변환된 테스트 케이스가 도구 내에서 정상적으로 표시되고 실행 가능한지 확인합니다.

**Acceptance Scenarios**:

1. **Given** 사용자가 외부 테스트 케이스 파일(Excel, CSV, JSON)을 준비했을 때, **When** "파일 가져오기" 버튼을 클릭하여 파일을 업로드하면, **Then** 파일 형식이 자동으로 감지됩니다
2. **Given** 파일이 업로드되었을 때, **When** 파일 내용이 파싱되면, **Then** 테스트 케이스 데이터가 도구의 표준 포맷(테스트 ID, 설명, 단계, 예상 결과)으로 변환됩니다
3. **Given** 변환된 테스트 케이스가 생성되었을 때, **When** 사용자가 변환 결과를 확인하면, **Then** 원본 파일의 내용이 올바르게 매핑되었는지 미리보기로 확인할 수 있습니다
4. **Given** 변환이 완료되었을 때, **When** 사용자가 "가져오기 완료"를 클릭하면, **Then** 변환된 테스트 케이스가 테스트 케이스 목록에 추가되고 실행 가능한 상태가 됩니다

---

### Edge Cases

- 웹 서비스 로그인 실패 시 어떻게 처리되는가? (잘못된 인증 정보, 네트워크 오류)
- PRD 파일이 비어있거나 형식이 올바르지 않을 때 시스템은 어떻게 반응하는가?
- 테스트 실행 중 웹 서비스가 응답하지 않거나 타임아웃이 발생하면? → 각 단계 30초, 전체 테스트 5분 타임아웃 적용 후 실패 기록 및 다음 테스트 진행
- 동시에 여러 테스트 세션을 실행할 수 있는가? → 단일 세션만 지원, 새 세션 시작 시 기존 세션 중단 확인 필요
- 외부 테스트 케이스 파일의 형식이 도구가 지원하지 않는 구조일 때 어떻게 처리되는가?
- 테스트 실행 중 사용자가 중단 버튼을 클릭하면 어떻게 되는가?
- AI 증강 기능이 Gemini API 호출 제한에 도달하면? → 재시도 후 실패 시 기본 테스트 케이스로 진행하고 경고 표시

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 PRD 문서(Markdown, PDF 형식)를 업로드하고 파싱할 수 있어야 합니다
- **FR-002**: 시스템은 PRD 내용을 분석하여 자동으로 테스트 케이스를 생성해야 합니다
- **FR-003**: 시스템은 Gemini API를 통해 기존 테스트 케이스를 기반으로 추가 테스트 케이스 및 엣지 케이스를 생성할 수 있어야 합니다
- **FR-004**: 사용자는 테스트 케이스를 추가, 수정, 삭제할 수 있어야 합니다
- **FR-005**: 시스템은 Playwright MCP를 통해 웹 브라우저를 제어하여 웹 서비스에 접속하고 로그인할 수 있어야 합니다
- **FR-006**: 시스템은 테스트 케이스의 각 단계를 순차적으로 실행하고 결과를 기록해야 합니다
- **FR-007**: 시스템은 테스트 실행 중 스크린샷을 캡처하고 저장해야 합니다
- **FR-008**: 시스템은 모든 테스트 완료 후 QA 리포트를 생성해야 합니다
- **FR-009**: QA 리포트는 전체 성공률, 실패한 테스트 목록, 스크린샷, 오류 메시지를 포함해야 합니다
- **FR-010**: 시스템은 테스트 실행 중 실시간 진행 상황(진행률, 현재 테스트, 상태)을 표시해야 합니다
- **FR-011**: 시스템은 Playwright를 통해 제어되는 브라우저 화면을 사용자에게 보여줄 수 있어야 합니다 (Playwright headed 모드로 브라우저 창 표시, 추가로 현재 테스트 URL 및 상태 정보를 UI에 표시)
- **FR-012**: 시스템은 외부 테스트 케이스 파일(Excel, CSV, JSON)을 가져올 수 있어야 합니다
- **FR-013**: 시스템은 가져온 외부 파일을 도구의 표준 테스트 케이스 포맷으로 변환해야 합니다
- **FR-014**: 사용자는 테스트 실행을 중단할 수 있어야 합니다
- **FR-015**: 시스템은 테스트 케이스를 파일로 내보낼 수 있어야 합니다
- **FR-016**: 시스템은 이전 테스트 실행 히스토리를 조회할 수 있어야 합니다
- **FR-017**: 시스템은 웹 서비스 로그인 정보를 환경 변수 또는 암호화된 설정 파일에 안전하게 저장해야 합니다
- **FR-018**: 시스템은 저장된 로그인 정보에 접근할 때 적절한 권한 검증을 수행해야 합니다
- **FR-019**: 시스템은 Gemini API 호출 실패 시 자동으로 재시도해야 합니다
- **FR-020**: Gemini API 재시도 실패 또는 호출 제한 도달 시 기본 테스트 케이스로 진행하고 사용자에게 경고를 표시해야 합니다
- **FR-021**: 시스템은 한 번에 하나의 테스트 세션만 실행할 수 있습니다
- **FR-022**: 새 테스트 세션 시작 시 기존 실행 중인 세션이 있으면 사용자에게 중단 확인을 요청해야 합니다
- **FR-023**: 시스템은 테스트 실행 결과를 최근 30일간 보관해야 합니다
- **FR-024**: 시스템은 30일이 경과한 테스트 결과를 자동으로 삭제해야 합니다
- **FR-025**: 시스템은 각 테스트 단계에 30초 타임아웃을 적용해야 합니다
- **FR-026**: 시스템은 전체 테스트 케이스에 5분 타임아웃을 적용해야 합니다
- **FR-027**: 타임아웃 발생 시 시스템은 해당 테스트를 실패로 기록하고 다음 테스트로 진행해야 합니다
- **FR-028**: 모든 서비스 레이어 로직은 유닛 테스트로 검증되어야 합니다 (헌법 원칙 I - 테스트 우선 개발)
- **FR-029**: 모든 API 엔드포인트는 계약 테스트로 검증되어야 합니다 (헌법 원칙 III - 통합 테스팅)
- **FR-030**: 핵심 사용자 워크플로우(PRD 업로드→테스트 생성→실행→리포트)는 E2E 통합 테스트로 검증되어야 합니다

### Key Entities

- **PRD (Product Requirements Document)**: 제품 요구사항 문서로, 파일명, 업로드 시간, 파일 형식, 파싱된 텍스트 내용을 포함합니다
- **TestCase (테스트 케이스)**: 개별 테스트 항목으로, 테스트 ID, 설명, 실행 단계 목록, 예상 결과, 생성 출처(PRD 자동 생성/AI 증강/사용자 수동 추가)를 포함합니다
- **TestStep (테스트 단계)**: 테스트 케이스 내의 개별 실행 단계로, 단계 번호, 동작 설명, 예상 결과를 포함합니다
- **EdgeCase (엣지 케이스)**: 경계 조건 및 예외 상황 테스트로, TestCase의 특수 유형입니다
- **TestSession (테스트 세션)**: 테스트 실행 단위로, 세션 ID, 시작 시간, 종료 시간, 대상 웹 서비스 URL, 실행된 테스트 케이스 목록, 전체 결과, 보관 만료일(생성일 + 30일)을 포함합니다
- **TestResult (테스트 결과)**: 개별 테스트의 실행 결과로, 테스트 케이스 ID, 성공/실패 상태, 실패 사유, 스크린샷 경로, 실행 시간을 포함합니다
- **QAReport (QA 리포트)**: 테스트 세션의 종합 리포트로, 전체 테스트 개수, 성공 개수, 실패 개수, 성공률, 실패한 테스트 상세 정보, 생성 시간을 포함합니다
- **WebService (웹 서비스)**: 테스트 대상 웹 서비스로, URL, 로그인 정보(환경 변수 또는 암호화된 설정 파일에 저장), 테스트 대상 페이지 경로를 포함합니다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 PRD 업로드부터 QA 리포트 생성까지 전체 프로세스를 10분 이내에 완료할 수 있습니다 (PRD 파싱 + 테스트 케이스 생성 시간만 포함, 실제 테스트 실행 시간 제외)
- **SC-002**: AI 기반 테스트 케이스 증강 기능은 기본 테스트 케이스 대비 최소 30% 이상의 추가 테스트 케이스를 생성합니다
- **SC-003**: 테스트 실행 중 진행 상황이 5초 이내에 업데이트되어 실시간으로 표시됩니다 (WebSocket 이벤트 발신부터 클라이언트 UI 렌더링까지 전체 지연시간 기준)
- **SC-004**: 외부 테스트 케이스 파일 가져오기 성공률이 90% 이상입니다 (지원 형식에 한함)
- **SC-005**: 생성된 QA 리포트는 모든 필수 정보(성공률, 실패 목록, 스크린샷)를 포함하며 사용자가 1분 이내에 핵심 결과를 파악할 수 있습니다
- **SC-006**: 시스템은 최소 50개의 테스트 케이스를 30분 이내에 실행 완료할 수 있습니다
- **SC-007**: 도구 사용 후 QA 테스트 준비 시간이 기존 대비 50% 이상 단축됩니다

## Clarifications

### Session 2025-10-21

- Q: 웹 서비스 로그인 정보(아이디/비밀번호)를 어떻게 저장하고 관리해야 할까요? → A: 환경 변수 또는 안전한 설정 파일에 암호화하여 저장
- Q: Gemini API 호출이 실패하거나 호출 제한에 도달했을 때 어떻게 처리해야 할까요? → A: 재시도 후 실패 시 기본 테스트 케이스로 진행하고 경고 표시
- Q: 동시에 여러 테스트 세션을 실행할 수 있어야 할까요? → A: 단일 세션만 지원, 새 테스트 시작 시 기존 실행 중단 필요
- Q: 테스트 실행 결과와 히스토리를 얼마나 오래 보관해야 할까요? → A: 최근 30일간 테스트 결과 보관, 이후 자동 삭제
- Q: 각 테스트 단계의 타임아웃을 얼마로 설정해야 할까요? → A: 각 단계 30초, 전체 테스트 5분
